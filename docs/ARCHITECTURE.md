## 1. What the system does

A data and reporting platform for Toesca's three real-estate funds (**TRI**, **PT**,
**Apo**) and their ~10 underlying assets. One SQLite database
(`memory/agente_toesca_v2.db`) is the single source of business-financial truth, replacing
a monthly 14 MB Excel workflow ("the CDG") that is in active decommission (per the
archived `ROADMAP.md`'s F1.7).

## 3. Data layer

**Layers** (full table-by-table detail belongs in code/migrations, not restated here to
avoid a fourth copy of the schema — see `tools/db/migrations/` for ground truth):

| Layer | Pattern |
|---|---|
| Dimensions (`dim_*`) | Master catalogs: fondo, activo, serie, sociedad, credito, cuenta_eeff |
| Raw lines (`raw_*_line`) | One row per source-document line; full lineage (`source_file`, `file_hash`, `ingest_run_id`, `loaded_at`, `superseded_at`) |
| Raw observations (`raw_*`, no `_line`) | Snapshots/events: caja, dividendo, valor_cuota, saldo_deuda, amortizacion, and (new, JLL v2) cartera, recaudacion |
| Facts (`fact_*`) | Derived facts: adquisicion, tasacion |
| Derived (`derived_kpi`) | KPI cache, keyed by entidad_tipo + kpi + variante + formula |
| Audit (`ingest_run`, `schema_version`) | Load traceability |

**Governance/semantic layer**: `semantic/` (domains, entities, metrics, relationships,
synonyms) and `tools/datasets/` (`catalog.py`, `catalog_v1.yaml`, `executor.py`) define a
governed dataset contract. This is the layer both the Analyst and the planned
deterministic report generators (`docs/ROADMAP.md`'s Product Shell & Reporting v1) are
meant to share — one metrics definition, not two.

**Versioning convention**: append-only with logical tombstones. A new file version →
new rows + `mark_superseded()` on the old file's hash; every business-logic read filters
`superseded_at IS NULL`. This is a repo-wide invariant, not specific to any one table.

## 4. JLL v2 ingestion pipeline (added this branch)

See `docs/CURRENT_STATE.md`'s JLL v2 section for the implemented/production/Analyst-facing
three-way distinction — not restated here. Architecturally, this pipeline follows the same
raw-line + lineage + versioned-rules pattern as the rest of the data layer, extended with:
a bridge table (`raw_er_movimiento_lineage`) for N:1 movement→ER-line provenance, and a
separate versioned-rules table (`dim_er_regla_interna`) for internally-authoritative
accounts JLL doesn't provide, with fail-closed precedence in the derivation code
(`tools/db/derive_er_jll_v2.py`) — it never silently overrides an internal rule with a
provider value if the rule isn't evaluable.

## 5. Analyst runtime

Two separable concerns, deliberately kept apart (see each module's own docstring for the
enforced boundary):

- **Reasoning policy** (`tools/analyst_runtime/analyst_loop.py`): round budget, when
  investigation gives way to synthesis, turn assembly. Imports nothing from a specific
  provider SDK (`openai`, `anthropic`) and nothing SQL-specific — it receives a
  `ToolRequest` and returns whatever the injected `ActionExecutor` gives back.
- **Wire-protocol translation** (`tools/analyst_runtime/transport.py`): the
  `ModelTransport` seam between the reasoning loop and whichever provider is actually
  configured (Chat Completions, OpenAI Responses, Anthropic Messages have each needed
  this at different points — see `eval/round_b/` adapters).
- **Guards** (`canonical_guard.py`, `coverage_guard.py`, `sqlite_guard.py`): enforce that
  claims are backed by governed data with explicit coverage checks before they reach a
  user. Not independently line-by-line verified in the Pass 1/1.5 audits — verify before
  treating this as a safety guarantee in a new design.
- **Conversation persistence** (`tools/analyst_workspace/`): a separate module from the
  reasoning loop — `conversation_service.py`, `store.py`, `admin.py`,
  `export_markdown.py`. This is why `tools/analyst_api.py` supplies the service via a lazy
  factory rather than constructing it directly: HTTP tests and module imports stay free of
  workspace/provider/DB side effects.

## 6. LLM / provider surfaces

Per `config.py`: `GEMINI_API_KEY`, `MISTRAL_API_KEY`, `SAMBANOVA_API_KEY`,
`DEEPSEEK_API_KEY`, `GROQ_API_KEY` (+ two extra Groq accounts for quota), and
`DB_CHAT_PROVIDER` (default `groq`, fallback chain `deepseek → groq → gemini → mistral →
sambanova`) for the prior-generation `db_chat.py` path. `agent.py` (legacy) targets Gemini
2.5 Flash directly. `tools/analyst_runtime/` is deliberately provider-neutral — it is
**not** wired to any specific provider by design, which is why no Anthropic/Claude client
exists in this codebase despite `transport.py` referencing Anthropic's wire protocol as
one of the shapes it can translate.

## 7. Security

Not independently re-verified for this document. The archived `system_architecture.md`
§7 describes token-auth on all `/api/*` routes, restricted CORS, path-traversal
protections, and (as an open item at that time) `POST /api/chat` accepting
client-controlled history with no server-side logging. Whether those specific claims
still hold at this SHA was not re-checked — treat §7 there as a starting point for
re-verification, not as current fact.

The archived `system_architecture.md` kept an explicit "documentation vs. code vs. DB"

document or `docs/CURRENT_STATE.md` is found to disagree with actual code/migrations/

correction, not silent rewriting, is the standard this documentation reset itself was
built to uphold.
